**V4.4 · 2026-09-11 · GNOMON BASELINE V4.4**

## Abstract

This document defines the P1 layer of GnomonSystem: the Prime Protocol.
Prime addresses two questions:

**Question 1 (single domain):** How can physical time, as measured by atomic clocks, be cryptographically transformed into a verifiable digital timeline?

**Question 2 (multiple domains):** When multiple independent L1 node systems exist, how can their causal universes recognize one another without unifying their TI spaces?

Core principles:

- The root of trust for temporal order is physical reality (cesium atomic transitions), not the reputation of any institution.
- Multiple L1 systems are parallel causal universes and do not require global time synchronization.
- Cross-domain causality is established naturally through the contact surface of collaborative events; a unified clock is not required.

## 1. Terms and notation

### 1.1 Core terms

**Physical Time:**
The time reference provided by an atomic clock (the cesium-133 hyperfine transition).
Distributed through the National Time Service Center (NTSC) or the BeiDou system.
Unit: nanoseconds (ns).

**TemporalIndex (TI):**
A discretized mapping of physical time within a specific L1 domain.
A monotonically increasing `uint64` integer, globally unique within the domain.
Approximately 1 microsecond per TI (configurable for the deployment).
TI is not absolute physical time; it is an engineering representation of causal order.

**Causal Universe:**
A node network that shares the same L1 node trust root.
Events within one causal universe have comparable TI values (authorized uniqueness); this does not guarantee physical-time ordering (causal partial order).
Events in different causal universes do not need to be ordered against one another (a partial order is sufficient).

**Contact Surface:**
A connection point established between two causal universes through a cross-domain collaborative event.
After a contact surface is established, the ordering of cross-universe events can be traced through event references.

**RootTHK (Root TimeHashKey):**
A physical-time cryptographic anchor generated by an L1 node every hour.
Anchors real physical time with precision of at most 20 ns.
Allocates a large TI range covering the entire hour.

**ChildTHK:**
A high-frequency temporal credential derived from a RootTHK.
Issued on demand and may be triggered every second or every minute.
Allocates a small TI range covering a specific business window.
Inherits the physical-time authority of its RootTHK.

**Federation:**
A mutual-recognition network formed when multiple independent L1 causal universes sign a federation charter.
Comparable to the ITU as a multilateral body: all members are equal, and there is no global root node.

### 1.2 Notation

`H(·)` — SM3 hash function (256-bit output)  
`Sign(sk, ·)` — SM2 signature  
`Verify(pk, m, σ)` — SM2 verification, returning `{0,1}`  
`BE64(n)` — 64-bit big-endian integer encoding  
`∥` — byte-string concatenation  
`rTHK` — RootTHK  
`cTHK` — ChildTHK  
`KP_v` — KeyPackage for L2 node `v`  
`TI_v` — current TemporalIndex of node `v`  
`FC` — FederationCharter  
`FMR` — FederationMemberRecord  
`CSR` — CrossDomainContactRecord  
`OpCert` — Operation Certificate

## 2. Single-domain physical-time anchoring

### 2.1 Temporal hierarchy

The Prime Protocol uses a hierarchical THK design to balance physical-time precision with business flexibility:

```text
Physical time (atomic clock · precision ≤ 20 ns)
│
│ sampled once per hour
▼
RootTHK (Root TimeHashKey)
· anchors physical time
· TI allocation: each RootTHK covers 3,600,000,000 TIs (about one hour)
· signed by the L1 node root key
│
│ derived on demand (using an operational key)
▼
ChildTHK
· derived from a RootTHK and inherits its physical-time authority
· TI allocation: each ChildTHK covers 1,000,000 TIs (about one second), or a custom range
· signed by an L1 node operational key (the operational key receives a short-lived certificate from the root key)
· use cases: high-frequency financial settlement, real-time AI decisions, and millisecond-scale event sequences
│
│ KeyPackage distribution
▼
L2 node (uses TI to issue EEA)
```

**Why the hierarchy is necessary:**

If there were only RootTHKs (one per hour):
L2 nodes would use the same TI range for an entire hour.
High-frequency scenarios (60,000 TPS × 3,600 s = 216 million EEAs) need a sufficiently large TI range.
A RootTHK cannot represent temporal order precisely within the hour.

If there were only ChildTHKs (issued on demand):
Each business operation would have to wait for the L1 to issue one, causing high latency (an HSM signature takes at least 2 ms).
The L1 would become a hot spot and a performance bottleneck.

With the hierarchical design (RootTHK + ChildTHK):
RootTHK: one per hour, anchoring physical time precisely.
ChildTHK: issued on demand, inheriting RootTHK authority and subdividing the TI range.
L2 node: once it holds a KeyPackage (which carries a ChildTHK), it can issue EEAs locally at high speed within that ChildTHK's TI range.

### 2.2 RootTHK (Root TimeHashKey)

**Data structure (176 B):**

| Field | Length | Type | Description |
|---|---:|---|---|
| `t_utc` | 8 B | `uint64` BE | UTC time (nanoseconds) |
| `t_epoch` | 8 B | `uint64` BE | Starting TI value for this RootTHK |
| `ti_range_start` | 8 B | `uint64` BE | First TI covered by this RootTHK |
| `ti_range_end` | 8 B | `uint64` BE | End of the TI range covered by this RootTHK (exclusive) |
| `nonce` | 16 B | `bytes` | CSPRNG-generated random value |
| `prev_root_commitment` | 32 B | `bytes` | Time commitment of the preceding RootTHK |
| `time_commitment` | 32 B | `bytes` | Time commitment of this RootTHK |
| `root_thk_signature` | 64 B | `bytes` | SM2 signature by the L1 root key |
| **Total** | **176 B** |  |  |

**Compute `time_commitment`:**

```text
time_commitment = H(
    BE64(t_utc) ∥             // physical time (nanoseconds)
    BE64(t_epoch) ∥          // starting TI value
    l1_node_id(32 B) ∥       // L1 node identifier (SM3(L1 public key))
    nonce(16 B)              // random salt
)
```

**Signing payload for `root_thk_signature`:**

```text
signing_payload =
    "Prime.RootTHK.v1"(16 B) ∥
    BE64(t_utc) ∥
    BE64(t_epoch) ∥
    BE64(ti_range_start) ∥
    BE64(ti_range_end) ∥
    prev_root_commitment(32 B) ∥
    time_commitment(32 B)
root_thk_signature = Sign(sk_root_L1, H(signing_payload))
```

**RootTHK chain-integrity rules:**

For all `n ≥ 1`:

```text
rTHK_n.prev_root_commitment = rTHK_(n-1).time_commitment
rTHK_n.ti_range_start = rTHK_(n-1).ti_range_end
rTHK_n.t_utc > rTHK_(n-1).t_utc
Verify(pk_root_L1, rTHK_n) = 1
```

Genesis RootTHK (`n = 0`):
`prev_root_commitment = 0x00 × 32`  
`ti_range_start = 1` (TI starts at 1; 0 is reserved)

### 2.3 ChildTHK

A ChildTHK is derived from a RootTHK and is intended for high-frequency business scenarios and fine-grained temporal requirements. A ChildTHK is signed with an operational key (see §2.4).

**Data structure (208 B):**

| Field | Length | Type | Description |
|---|---:|---|---|
| `parent_root_thk_id` | 32 B | `bytes` | `time_commitment` of the parent RootTHK |
| `t_utc` | 8 B | `uint64` BE | Physical time at issuance (nanoseconds) |
| `ti_range_start` | 8 B | `uint64` BE | Start of the TI range covered by this ChildTHK |
| `ti_range_end` | 8 B | `uint64` BE | End of the TI range covered by this ChildTHK (exclusive) |
| `sub_sequence` | 4 B | `uint32` BE | Sequence number of this ChildTHK under its parent THK (starting at 1) |
| `max_issuance_delay` | 4 B | `uint32` BE | TI-use validity period in seconds. Aggregated with `sub_sequence` into an 8-byte control block. From the time the ChildTHK is issued, each TI in its range MUST be used to issue an EEA within `max_issuance_delay` seconds. A verifier rejects a TI used after this period. `0` means unlimited validity (for backward compatibility). This constrains an L2 node to consume an assigned TI range on time after receipt, but does not constrain differences in parallel consumption rates between L2 nodes. |
| `target_node_fp` | 32 B | `bytes` | Target L2 node fingerprint (all zeros means generic) |
| `nonce` | 16 B | `bytes` | CSPRNG-generated random value |
| `child_commitment` | 32 B | `bytes` | ChildTHK commitment |
| `child_thk_signature` | 64 B | `bytes` | SM2 signature by the L1 operational key |
| **Total** | **208 B** |  |  |

Read directly from the fixed binary layout (Decision 019). There is no dual Protobuf representation.

**Compute `child_commitment`:**

```text
child_commitment = H(
    parent_root_thk_id(32 B) ∥
    BE64(t_utc) ∥
    BE64(ti_range_start) ∥
    BE64(ti_range_end) ∥
    BE32(sub_sequence) ∥
    BE32(max_issuance_delay) ∥
    nonce(16 B)
)
```

**Signing payload for `child_thk_signature`:**

```text
signing_payload =
    "Prime.ChildTHK.v1"(17 B) ∥
    parent_root_thk_id(32 B) ∥
    BE64(t_utc) ∥
    BE64(ti_range_start) ∥
    BE64(ti_range_end) ∥
    BE32(sub_sequence) ∥
    BE32(max_issuance_delay) ∥
    target_node_fp(32 B) ∥
    child_commitment(32 B)
child_thk_signature = Sign(sk_op_L1, H(signing_payload))
```

**ChildTHK replay protection:**

- An L1 node MUST record the largest `sub_sequence` issued under each parent RootTHK. A newly issued ChildTHK MUST have `sub_sequence = max + 1`.
- ChildTHK issuance history MUST be stored persistently for at least 30 days.
- A verifier SHOULD check whether it has already seen the same `(parent_root_thk_id, sub_sequence)` pair; if so, it MUST reject the ChildTHK (return `E009`).

### 2.4 Operational-key certificate (OpCertificate)

The operational key (`sk_op_L1`) is separate from the root key (`sk_root_L1`) and is used to issue ChildTHKs; it can be rotated more frequently. An OpCertificate conveys trust in the operational key.

**OpCertificate structure (216 B):**

| Field | Length | Type | Description |
|---|---:|---|---|
| `op_cert_id` | 32 B | `bytes` | `H("Prime.OpCertID.v1" ∥ issuer_root_fp ∥ op_pubkey ∥ valid_from ∥ valid_until ∥ key_version_op ∥ allowed_ops)` |
| `issuer_root_fp` | 32 B | `bytes` | Issuing L1 root fingerprint |
| `op_pubkey` | 64 B | `bytes` | Operational public key (SM2) |
| `valid_from` | 8 B | `uint64` BE | Starting TI at which the certificate is valid |
| `valid_until` | 8 B | `uint64` BE | Ending TI at which the certificate expires |
| `key_version_op` | 4 B | `uint32` BE | Operational-key version |
| `allowed_ops` | 2 B | `uint16` BE | Permitted operation: `0x01` = issue ChildTHK |
| `reserved_future` | 2 B | `bytes` | MUST be zero; aggregated with `key_version_op` and `allowed_ops` into an 8-byte control block (`uint32` → `uint16` → padding) |
| `root_sig` | 64 B | `bytes` | SM2 signature by the root key |
| **Total** | **216 B** |  | Fixed binary layout read directly (Decision 019) |

**OpCertificate signing payload:**

```text
signing_payload =
    "Prime.OpCert.v1"(15 B) ∥
    issuer_root_fp(32 B) ∥
    op_pubkey(64 B) ∥
    BE64(valid_from) ∥
    BE64(valid_until) ∥
    BE32(key_version_op) ∥
    BE16(allowed_ops) ∥
    reserved_future(2 B) MUST=0
root_sig = Sign(sk_root_L1, H(signing_payload))
```

**Trust chain for ChildTHK validation:**

When validating a ChildTHK, a verifier MUST perform the following steps:

Step 1: Verify that the RootTHK identified by `parent_root_thk_id` exists and is valid.  
Step 2: Verify that the OpCertificate is valid:

1. `root_sig` is valid (signature by the root key).
2. `valid_from ≤ current_TI < valid_until`.
3. `allowed_ops` includes `0x01` (issue ChildTHK).

Step 3: Use `OpCertificate.op_pubkey` to verify `child_thk_signature`.  
Step 4: Verify that the ChildTHK TI range is within the parent RootTHK range.

A ChildTHK issued by an operational key without a valid OpCertificate is invalid (`E005`).

### 2.5 Rules for using hierarchical THKs

**Rule 1: TI ranges MUST NOT overlap**

Within one L1 domain, the TI ranges of all RootTHKs and ChildTHKs MUST NOT overlap.
The L1 node maintains a persistent TI-allocation registry to prevent duplicate allocations.

**V4.1 security revision: persistent L1 state**

The following L1 state MUST be stored persistently. Use a WAL (Write-Ahead Log) to ensure crash safety. On restart, recover from a persistent checkpoint; do not rebuild state from `initial_counter`.

| State | Persistence method | Crash recovery |
|---|---|---|
| `epoch_id` | WAL write → fsync → commit | Recover the last committed epoch after restart |
| KeyPackage issuance records | WAL + snapshot | Recover all valid KPs |
| Node registry | WAL + snapshot | Recover the registry; reset heartbeat times |
| TI allocator checkpoint | fsync after every allocation | Prevent duplicate TI issuance after restart |

See RFC-SEC-001 §2 for the Tier-1 control-plane authentication model.

Allocation requests MUST be recorded in the registry. Requests spanning multiple nodes are serialized.

**Rule 2: A ChildTHK TI range MUST be within its parent RootTHK range**

```text
cTHK.ti_range_start ≥ rTHK.ti_range_start
cTHK.ti_range_end ≤ rTHK.ti_range_end
```

**Rule 3: L2 nodes MUST be able to validate the ChildTHK carried by a KeyPackage**

When an L2 node receives a KeyPackage (carrying one ChildTHK), it MUST verify:

1. `KeyPackage.package_signature` is valid (signature by the L1 root key).
2. `KeyPackage.target_node_fp` equals the node's own fingerprint (confirming that the credential was issued to this node).
3. The ChildTHK corresponding to `KeyPackage.child_thk_commitment` has a valid `child_thk_signature` (operational key and OpCertificate chain).
4. The RootTHK identified by the ChildTHK's `parent_root_thk_id` exists and is valid (root key).
5. The ChildTHK TI range is within the RootTHK range.

An L2 node does not receive a bare ChildTHK; the ChildTHK is delivered inside a KeyPackage.

**Rule 4: Restrictions on generic ChildTHKs (`target_node_fp = all zeros`)**

A generic ChildTHK can be used by any L2 node.
To prevent abuse, an L1 node SHOULD limit the length of a generic ChildTHK TI range (recommended: no more than 10,000 TIs).
An L2 node using a generic ChildTHK MUST verify that it has not been revoked.
Prefer issuing a ChildTHK bound to the requesting node fingerprint (`target_node_fp = requesting node fingerprint`).

**Rule 5: Physical-time precision declared by a ChildTHK**

The precision of a ChildTHK's `t_utc` is the time at which the L1 operational key issued it.
It is not guaranteed to differ from `RootTHK.t_utc` by no more than 20 ns.
The actual precision declaration is in the reserved extension field `ChildTHK.nanos_precision`.

**Rule 6: Degraded operation (KeyPackage grace period)**

Degraded operation is defined uniformly as the **KeyPackage grace period**. There is no path in which an L2 node directly issues credentials from a RootTHK (the RootTHK is an L1 physical anchor and is not held by L2; moreover, its one-hour granularity cannot meet high-frequency timing-precision requirements):

- Normal: `current_wallclock < KeyPackage.valid_until` → `degraded_mode = 0`.
- Grace period: `valid_until ≤ current_wallclock < valid_until + grace_period`:
  - `degraded_mode = 1`; the L2 node may continue to issue EEAs using the remaining TI range of the ChildTHK carried by its current KeyPackage.
  - The EEA is marked as degraded, indicating: “issued while the L1 connection was unavailable; calibration is pending.”
- Grace period exceeded: `current_wallclock ≥ valid_until + grace_period`:
  - The L2 node MUST stop issuing and request a new KeyPackage (carrying a new ChildTHK) from the L1.

Note: During the grace period, TI values still come from the ChildTHK's `ti_range`; `degraded_mode` only marks an abnormal credential-renewal condition and does not change the basis for TI allocation.

### 2.6 KeyPackage

A KeyPackage is a temporal-use credential issued by an L1 node to a Tier-2 (L2) node. It **carries one ChildTHK** and is bound to a specific L2 node. An L2 node holds a KeyPackage as its **only temporal credential** for issuing EEAs: `child_thk_commitment` binds the KeyPackage to its carried ChildTHK, and the EEA's TemporalIndex is taken from that ChildTHK's TI range. The Tier-2 node's identity is checked through the NodeCertificate and the KeyPackage synchronization-request chain.

**Relationship between a KeyPackage and a ChildTHK (V2.4):**

- RootTHK (physical anchor, one hour) → ChildTHK (subdivided TI range, about one second / one million TIs) → KeyPackage (carries the ChildTHK and is bound to L2) → L2 issues EEAs locally at high speed.
- `KeyPackage.child_thk_commitment` references the `child_commitment` of its carried ChildTHK, and `package_signature` covers this field. The “KeyPackage ↔ ChildTHK” binding is therefore cryptographically tamper-evident.
- **Division of TI semantics:** `valid_until` is the KeyPackage **credential-expiration time** (a renewal signal with wall-clock semantics; L2 must request a renewal when it expires). The ChildTHK's `ti_range_start/end` define the **TI allocation range** (the EEA's `TemporalIndex` must fall within that range). These meanings differ and are not duplicates.

**Data structure (224 B, V2.4 final):**

| Field | Length | Type | Description |
|---|---:|---|---|
| `t_epoch` | 8 B | `uint64` BE | TI at issuance |
| `valid_until` | 8 B | `uint64` BE | Credential expiration TI (exclusive; renewal signal) |
| `grace_period_seconds` | 4 B | `uint32` BE | Grace-period length in seconds |
| `key_version` | 4 B | `uint32` BE | L1 root-key version; aggregated with `grace_period` into an 8-byte control block |
| `issuer_node_id` | 32 B | `bytes` | L1 issuer node ID |
| `root_public_key_hash` | 32 B | `bytes` | Hash of the L1 issuer root public key |
| `issued_at` | 8 B | `uint64` BE | Issuance time in Unix milliseconds |
| `child_thk_commitment` | 32 B | `bytes` | `child_commitment` of the carried ChildTHK (added in V2.4) |
| `target_node_fp` | 32 B | `bytes` | Bound L2 node fingerprint (added in V2.4) |
| `package_signature` | 64 B | `bytes` | SM2 signature by the L1 root key |
| **Total** | **224 B** |  | Fixed binary layout read directly (Decision 019) |

**KeyPackage signing payload:**

```text
signing_payload = KeyPackagePayloadV2_4

KeyPackagePayloadV2_4 = (
    BE64(t_epoch) ∥
    BE64(valid_until) ∥
    BE32(grace_period_seconds) ∥
    BE32(key_version) ∥
    issuer_node_id(32 B) ∥
    root_public_key_hash(32 B) ∥
    BE64(issued_at) ∥
    child_thk_commitment(32 B) ∥
    target_node_fp(32 B)
)
Payload length: 160 B
package_signature = Sign(sk_root_L1, H(signing_payload))
```

**KeyPackage validity predicate:**

```text
Valid(KP, t_wallclock, ti) ⟺
Verify(pk_root_L1, H(signing_payload), package_signature) = 1
∧ key_version = current_key_version(L1)
∧ issuer_node_id ∈ trusted_issuer_registry
∧ the ChildTHK referenced by KP.child_thk_commitment exists and is valid
∧ ti ∈ [ChildTHK.ti_range_start, ChildTHK.ti_range_end)   ← EEA.TI falls within the ChildTHK range
∧ t_wallclock < valid_until                          ← credential has not expired (renewal signal)
```

Note: The basis for validating TI is the ChildTHK's `ti_range` (not the KeyPackage's `t_epoch` or `valid_until`). `valid_until` is used only to determine whether the credential needs renewal.

**§2.6.1 Credential rules for L2 EEA issuance (single-credential principle):**

When issuing an EEA, an L2 node holds **one KeyPackage** as its only temporal credential. The issuance flow is entirely local and does not interact with the L1; this is the source of the efficiency of the hierarchical design:

1. The L2 node validates its KeyPackage: `target_node_fp == its own node fingerprint`, `package_signature` is valid, and the package has not expired.
2. It obtains the TI range `[ti_range_start, ti_range_end)` of the ChildTHK carried by the KeyPackage.
3. It allocates TemporalIndex values locally and monotonically within that range.
4. It issues the EEA using the L2 node's own private key: `DigitalSignature = Sign(sk_L2_node, ...)`.
5. It does not request anything from the L1 during this process. One ChildTHK/KeyPackage request supports all high-speed issuance within that TI range.

Roles of the three credentials (to remove ambiguity):

- RootTHK: L1 physical-time anchoring credential; **used by the L1 and not distributed to L2**.
- ChildTHK: source of the TI allocation range; carried inside the KeyPackage distributed to L2.
- KeyPackage: the **only issuance credential held by L2**, internally bound to one ChildTHK.

An L2 node **does not directly hold a RootTHK** and does not hold a bare ChildTHK; it recognizes only the KeyPackage.

### 2.7 TemporalIndex allocation

**Allocation principles:**

TI space: `uint64`, approximately `1.8 × 10¹⁹` values.  
At one microsecond per TI, this supports 584,942 years; there is no capacity bottleneck.

Allocation strategy:

The L1 node maintains a global TI allocation registry (`ti_allocation_registry`).
Each allocation records `{recipient fingerprint, ti_range_start, ti_range_end, allocation time}`.
The registry is stored persistently and synchronized periodically between primary and standby nodes.

RootTHK allocation:

Allocate 3,600,000,000 TIs each time (covering one hour).
In practice, allocation is demand-driven and supports smaller or larger ranges.

ChildTHK allocation (on-demand scenarios):

Scenario A: high-frequency business nodes (finance · AI)
Request: 1,000,000 TIs per request (about one second).
Frequency: on demand, at most 100 times per second (to prevent the L1 from becoming a hot spot).

Scenario B: batch event processing
Request: 100,000,000 TIs (about 100 seconds).
Applicable to: offline batch processing and counter-signing scenarios.

Allocation-collision detection:

The L1 node MUST detect overlapping TI ranges.
For an overlapping request, return `E004` (TI-range conflict) and recommend requesting the next contiguous free range.

TI comparability:

TI values are guaranteed to be unique by authorization and monotonically increasing within one L1 domain. Different L2 nodes receive ranges from the same TI pool; the relative sizes of those ranges reflect the L1 allocation order, and TIs are allocated in numeric order within each range. Therefore, the TI values of any two EEAs within one L1 domain can be compared directly as numbers.

However, “numerically comparable” does not mean “comparable in physical time”:

- Between events with a causal link (referenced through ChainProof), TI represents a definite, provable order: a successor event must be issued after the event it references, and TI strictly increases.
- Between events without a causal link, TI values can be compared numerically but do not represent their physical issuance order. With parallel consumption, an EEA with a smaller TI may be issued later in physical time than one with a larger TI. Such events form a partial order; their relative order is undefined (see P2 §3.4.2).

To obtain the physical issuance time of an event, trace its EEA.TI back to the associated `ChildTHK.t_utc` (range-level precision). Higher precision (event-level) requires an independent request to the National Time Service Center; an EEA itself does not carry a per-event `t_utc` field.

TI spaces across multiple L1 domains:

Different L1 domains have independent TI spaces, which may overlap. This is central to the causal-universe design: TI values from different universes are not comparable.
The relative order of cross-domain events is established by contact-surface records (CSR), not by comparing TI values.

### 2.8 KeyPackage renewal and consumption reporting

Before a KeyPackage expires, an L2 node MUST request a renewal from the L1 and obtain a new KeyPackage.

**A renewal request MUST include a consumption summary for the preceding TI range:**

```text
ConsumptionSummary:
  prev_kp_id          32 B    package_signature or unique ID of the preceding KeyPackage
  ti_consumed         uint32  number of TIs actually consumed in the preceding range
  last_eea_anchor_id  32 B    AnchorID of the last EEA in the preceding range
  last_eea_ti         uint64  TemporalIndex of that EEA
```

**L1 validation rules:**

1. Use `last_eea_anchor_id` to trace the L2 EEA chain and verify its integrity through ChainProof.
2. Count the EEAs actually issued in the preceding TI range and compare that count with `ti_consumed`.
3. Calculate utilization = `ti_consumed / (ti_range_end - ti_range_start)`.
4. If utilization is 0, the L1 MAY reject renewal (an unused TI range indicates no demand).
5. The L1 records the utilization in the reputation registry.

**Dynamic reputation adjustment:**

| Recommended utilization threshold | KeyPackage range size | KeyPackage validity period |
|---|---|---|
| ≥ 50% | Standard range | Standard validity period |
| < 50%, ≥ 10% | Standard range × 0.5 | Validity period × 0.5 |
| < 10% | Minimum range | Minimum validity period |
| 0 (two consecutive times) | MAY reject renewal | — |

**Design boundaries:**

- The L1 does not automatically punish; it only measures utilization and dynamically adjusts range size.
- Low utilization may reflect low business volume and does not necessarily indicate malicious behavior.
- Degradation is reversible: utilization recovers → reputation recovers → range size recovers.
- The L1 reputation registry is a public reference for all business systems. An L2 with persistently low utilization is naturally eliminated through market selection.
- This mechanism adds no fields and changes no binary layout. The consumption summary is passed as parameters in the KeyPackage renewal request.

**Known residual risks (transparency boundary):**

An L2 node's autonomous issuance authority necessarily carries two residual risks that cannot be eliminated. The protocol does not attempt technical defenses—malicious behavior cannot be technically controlled here—but makes the behavior visible and its cost calculable through transparency.

1. **Backdated TI signing:** While a KeyPackage is valid, an L2 node can issue an EEA using any unconsumed TI without following physical-time order. ChainProof integrity checks pass (the links are correct), TI monotonicity checks pass (the TI has not yet been used), and the renewal report passes (N TIs were consumed). The protocol layer cannot unconditionally detect whether a TI was consumed late relative to physical time.

2. **Delayed EEA publication:** An L2 node can withhold an EEA after legitimately issuing it. The EEA is cryptographically correct, and an outside party cannot determine the delay between issuance and publication.

**Application-layer transparency mechanisms:**

- A business system connects to multiple L2 nodes at the same time → obtains multiple EEAs for the same event → compares receipt timestamps with TI values → a smaller TI received later exposes a contradiction.
- A business system at the “receiving end” knows when each EEA arrived and is therefore the best witness to an L2 node's delay.

**Accountability boundaries:**

- Cross-L2 comparison can expose a contradiction: two L2 nodes assign TI values to the same event that differ beyond the normal window.
- Cross-L2 comparison cannot determine which node acted maliciously. This is the Two Generals' Problem: without a third honest node, attribution is impossible.
- Ecosystem attrition: business systems reject delayed or backdated EEAs and migrate to honest L2 nodes; persistent anomalies → lower L1 reputation → smaller ranges → natural elimination.

## 3. Single-domain node management

### 3.1 L1 node requirements

**Hardware requirements (MUST):**

Time service: BeiDou / dedicated NTSC time service, with precision of at most 20 ns.  
HSM: two Level 4 devices conforming to GM/T 0028 (primary + hot standby).  
Network: dedicated line, not connected to the public Internet.  
Physical security: dual-door access control in the machine room, video surveillance, and protection against electromagnetic leakage.

**Operational requirements (MUST):**

Two-person authorization: two authorized personnel must be present for every root-key operation.  
Key shares: store the root key as Shamir (3,5) shares.  
Key rotation: rotate the root key annually; run both keys in parallel during rotation (30-day overlap).  
Audit logs: record every signing operation and retain the records for 10 years.

Availability requirements:

Normal mode: 99.99% availability (no more than 53 minutes of downtime per year).  
Failover: automatic primary-to-hot-standby switch within 30 seconds.  
Degraded-mode trigger: enter degraded mode if disconnected from the time source for more than 5 minutes.

### 3.2 L2 node authentication

Application process:

Step 1: The L2 node operator submits an application, including the node public key, hardware attestation, and operating qualifications.  
Step 2: GnomonSystem Time Source Technology Co., Ltd. performs a technical review (hardware, software, and compliance).  
Step 3: If approved, the L1 node issues a NodeCertificate.  
Step 4: The L2 node enters a 30-day observation period during which anomalous behavior is monitored.  
Step 5: After passing the observation period, the node goes into production.

**Revocation (an operational decision; not triggered automatically by the protocol):**

An L1 operator may stop issuing new KeyPackages to an L2 node for the following governance reasons:

- Reports from multiple business systems that have been verified manually.
- A regulatory or law-enforcement order.
- Persistently anomalous reputation with no improvement (the reputation-adjustment mechanism in P1 RFC §2.8 cannot correct it).

After revocation:

- Existing EEAs remain cryptographically valid (their KeyPackage was valid when they were issued); history is immutable.
- The L2 node can no longer issue new EEAs (no new KeyPackage means no new TI range).
- Once the KeyPackage expires, all EEA chains from that L2 node naturally terminate.

The L1 operator makes the revocation decision manually. The protocol does not specify “when to revoke”; that is arbitration by human society, not programmable cryptographic logic.

NodeCertificate structure:

```text
node_fingerprint(32 B) = H(node_public_key)
node_level(1 B) = 2 (L2)
node_type(1 B) = see NodeType enum
valid_from(8 B) TI
valid_until(8 B) TI
allowed_ext_types(N × 2 B) list of permitted extension_type values
allowed_contact_signing(1 B) 0 = cannot sign CSR; 1 = can sign (see §4.4)
node_cert_signature(64 B) signature by the L1 root key
```

### 3.3 Degraded mode

**Trigger conditions:** The L2 node loses its connection to the L1 node, or the current KeyPackage is about to expire (remaining time is less than the grace period).

Degraded-mode procedure:

Step 1: The L2 node detects that its connection to the L1 is down or that its KeyPackage is about to expire.  
Step 2: Switch to a local logical clock (a monotonically increasing counter).  
Step 3: Set `degraded_mode = 1` on subsequently issued EEAs.  
Step 4: Generate a DegradedModeRecord (`extension_type = 0x0011`). Record the degraded-mode start TI, reason, and starting value of the local counter.  
Step 5: After the L1 connection is restored:

1. Request a new KeyPackage (including a TI compensation range for the degraded period).
2. Perform TI mapping (see the M3 formula in Implementation Example 5).
3. Broadcast the degraded-mode mapping table to associated L2 nodes.
4. Record the recovery time in DegradedModeRecord.

Handling degraded EEAs in high-security scenarios:

SHOULD accept them (rather than reject them outright), but mark them as “covering a degraded period.”  
MAY reject them in high-security judicial or financial scenarios; the verifier's policy determines this.  
On rejection, return `W005` (EEA from a degraded period).

## 4. Recognition between causal universes (Federation)

**Design premise: L1 nodes operate independently.** Each L1 node has its own atomic clock, and microscopic differences of several nanoseconds exist between them. Gnomon does not accept a design in which “L1 clusters synchronize to one common time”—NTP stratum-1 servers do not synchronize with one another either. L1 nodes do not elect, negotiate, vote, or exchange THKs with one another. Federation does not solve “clock alignment”; it solves “mutual trust and recognition,” allowing events in different causal universes to establish causal relationships without a unified TI space.

### 4.1 Federation principles

**Principle 1: Equal sovereignty**

Each L1 node system is an independent causal universe.
Federation members have equal standing; there is no global root node.
(Comparable to the equality of ITU member states; there is no “super-member.”)

**Principle 2: Independent TI spaces**

Different causal universes have independent TI spaces and do not need synchronization.
TI has meaning only within its own universe.
Ordering across universes is established through contact-surface records (CSR), not by comparing TI values.

Analogy to relativity:

Different reference frames have their own timelines.
Causality between reference frames is determined by the light cones of events (the contact surface).
There is no absolute simultaneity; only causal relationships are absolute.

**Principle 2 bis: Continuity of node-level quantities across universes**

When an L2 node switches L1s (changes its KeyPackage), node-level quantities remain continuous and are not reset:

| Quantity | After switching | Basis |
|---|---|---|
| ST (SequenceToken) | Strictly increases under the same OriginFP; it is not reset when changing universes | RFC-P2 §2.1 |
| ChainProof | The first anchor in the new universe MUST link to the last anchor in the old universe (the preceding anchor under the same OriginFP); it is not reset to Genesis | RFC-P2 §3.3 |

Only universe-level quantities (TI) are independent across universes (overlap is allowed; the relation is a partial order). Node-level continuity combined with universe-level independence provides the basis for identifying a “switch point”: a switch event is the link between two adjacent anchors on the chain whose KeyPackages trace to different L1s.

**Principle 3: Minimal mutual recognition**

Federation needs only three things:

1. **Mutual trust:** members trust one another's root public keys (through public-key exchange and anchoring in the FederationCharter).
2. **Mutual verification:** members can verify THK and EEA signatures from another member's system.
3. **Interconnection:** cross-domain collaborative events record their contact surface through a CSR signed by both parties.

The following are not required:

- A unified TI space.
- A time-synchronization protocol.
- A global consensus mechanism.
- Physical-time ordering of cross-domain events.

**Principle 4: Causal-universe boundaries**

Within the same causal universe: TI values are comparable (by authorized uniqueness), but physical-time ordering is not guaranteed.
Every event has a unique TI value; under parallel consumption, a TI value's magnitude does not equal physical ordering.

Between different causal universes: the relation is a partial order.
Without a cross-universe contact surface: events have no ordering relationship and cannot be compared.
With a cross-universe contact surface: the causal relationship of events after the contact surface can be traced through the CSR.

Formal definition:

Let `E_A ∈ Universe A` and `E_B ∈ Universe B`.  
`E_A ≺ E_B` (event A precedes event B) if and only if:

```text
∃ CSR contact surface such that E_A ≺ CSR.eea_A ∧ CSR.eea_B ≺ E_B
```

### 4.2 FederationCharter

A FederationCharter is a mutual-recognition agreement jointly signed by multiple L1 nodes and is the cryptographic foundation of a federation.

**FederationCharter structure:**

| Field | Length | Description |
|---|---:|---|
| `charter_id` | 32 B | `H(all contents)`; unique charter identifier |
| `charter_version` | 4 B | `uint32`, starting at 1 |
| `effective_ti` | 8 B | Charter effective time (TI in the initiating party's universe) |
| `expiry_ti` | 8 B | Charter expiration time (`0` means no expiration) |
| `member_count` | 2 B | `uint16`; number of members |
| `members[N]` | `N × 96 B` | For each member: `l1_fp(32 B) + l1_pubkey(64 B)` |
| `governance_rules_hash` | 32 B | `H(governance rules text)` |
| `amendment_threshold` | 1 B | Minimum number of approvals required to amend the charter |
| `charter_content_hash` | 32 B | `H(all preceding fields)` |
| `signatures[N]` | `N × 64 B` | One SM2 signature from each member |

Minimum configuration (2 members):

Fixed fields: 87 B.  
Member list: `2 × 96 B = 192 B`.  
Signature list: `2 × 64 B = 128 B`.  
Total: 407 B.

**Charter-signing rules:**

Each member signs the following payload:

```text
signing_payload =
    "Prime.FedCharter.v1"(19 B) ∥
    charter_id(32 B) ∥
    charter_content_hash(32 B) ∥
    member_l1_fingerprint(32 B)  // fingerprint of the signing member
signature = Sign(sk_root_L1_member, H(signing_payload))
```

Charter activation conditions:

All member signatures are valid.  
Once active, `charter_id` becomes the federation's trust anchor.

`amendment_threshold`:

SHOULD satisfy `ceil(member_count / 2) ≤ amendment_threshold ≤ member_count`.  
If unspecified, the default is `ceil(2 * member_count / 3)` (a supermajority).

Charter amendments:

At least `amendment_threshold` members MUST sign an amendment proposal.  
The proposal includes the original `charter_id`, the changes, and a new `charter_id`.  
Historical charters are retained permanently (append-only).

### 4.3 Federation member-recognition protocol

**Step 1: Public-key exchange**

The FederationCharter contains the root public keys (`l1_pubkey`) of all members.  
When a member joins the federation, its root public key is written into the charter.  
Public-key exchange is complete once all members have signed the charter.

Local storage:

Each L1 node maintains a `federation_trust_store`:

```text
{charter_id, member_l1_fp, member_l1_pubkey, valid_from, valid_until}
```

Trust source: a signed FederationCharter (cryptographically verifiable).

**Step 2: Cross-domain THK verification**

When an L2 node receives an EEA from Universe B:

If the EEA's `origin_fingerprint` corresponds to a known L2 node in Universe B:

Step 1: Look up the NodeCertificate of the L2 node in Universe B.  
Step 2: The NodeCertificate was issued with a signature from Universe B's L1 root key.  
Step 3: Universe B's L1 root key can be looked up in the FederationCharter (mutual recognition).  
Step 4: Verify the chain: `EEA → NodeCert → L1_B root public key → FederationCharter`.  
Step 5: If verification succeeds, the EEA is valid within Universe B (this does not make its time comparable with time in Universe A).

**Step 3: FederationMemberRecord (FMR) broadcast**

When federation membership changes (a new member joins, a member exits, or a root key is updated):
The initiating member issues an FMR and broadcasts it to all federation members.

FMR structure:

```text
charter_id(32 B)             associated FederationCharter
event_type(1 B)              0x01 = join; 0x02 = exit; 0x03 = key update
member_l1_fp(32 B)           fingerprint of the changed member
new_l1_pubkey(64 B)          new public key (only for a key update)
effective_ti(8 B)             effective time (TI in the initiating party's universe)
announcement_sig(64 B)       signature by the initiating member
quorum_sigsM                  confirmation signatures from other members (M ≥ amendment_threshold)
```

**THK invalidation after a federation member is expelled:**

After an expulsion resolution passes, the initiating member publishes an FMR (`event_type = 0x02`) containing a hash of the reason for expulsion.
After receiving the FMR, all federation members MUST immediately blacklist the L1 node's root public key and reject any new THKs issued by that node (including RootTHKs and ChildTHKs).

Historical THKs remain valid (time-cut principle): THKs and EEAs issued before the expulsion time can still be verified using the archived historical public key.

The blacklist is propagated by FMR broadcasts. Each member periodically retrieves the latest blacklist delta.

### 4.4 Handling cross-domain events

**Anchoring rules for a cross-domain collaborative event:**

When Subject A (in Universe A) collaborates with Subject B (in Universe B):

Option 1 (recommended): each universe anchors the event independently.
Subject A generates `EEA_A` at an L2 node in Universe A (with TI_A timing).  
Subject B generates `EEA_B` at an L2 node in Universe B (with TI_B timing).  
The two EEAs are associated through a CSR (below).

Option 2: anchor the event in one universe.
Both parties agree to use one party's universe to anchor the event.  
The other party accepts that universe's timeline as a reference.  
Applicable to an explicit principal–agent relationship (customer → service provider).

Principle:

There is no requirement to use a “neutral third-party universe.”  
The business layer decides the anchoring strategy.

**CrossDomainContactRecord (CSR):**

A CSR is a cryptographic record that establishes a causal relationship between two causal universes.

Structure:

| Field | Length | Description |
|---|---:|---|
| `csr_id` | 32 B | `H(all fields)` |
| `charter_id` | 32 B | Associated FederationCharter |
| `universe_a_l1_fp` | 32 B | L1 node fingerprint of Universe A |
| `universe_b_l1_fp` | 32 B | L1 node fingerprint of Universe B |
| `eea_a` | 32 B | AnchorID of the contact-surface EEA in Universe A |
| `eea_b` | 32 B | AnchorID of the contact-surface EEA in Universe B |
| `ti_a` | 8 B | TI value in Universe A (redundant; accelerates lookup) |
| `ti_b` | 8 B | TI value in Universe B (redundant) |
| `contact_type` | 2 B | Contact-surface type (see ContactType enum) |
| `contact_hash` | 32 B | `H(cross-domain collaborative content)` |
| `sig_a` | 64 B | Signature by the L1 node in Universe A (or an authorized L2 node) |
| `sig_b` | 64 B | Signature by the L1 node in Universe B (or an authorized L2 node) |
| **Total** | **372 B** |  |

`sig_a` signing payload:

```text
H("Prime.CSR.v1"(12 B) ∥ csr_id(32 B) ∥ eea_a(32 B)
  ∥ eea_b(32 B) ∥ BE64(ti_a) ∥ BE64(ti_b) ∥ contact_hash(32 B))
```

`sig_b` signing payload:

```text
sig_a signing payload(156 B) ∥ sig_a(64 B)  // nested; B covers A; total 220 B
```

Authorization requirements when an L2 node signs a CSR:

An L2 node signing a CSR MUST hold a NodeCertificate issued by an L1 node, and the certificate's `allowed_contact_signing` MUST equal 1.
An L1 node may delegate CSR signing to an L2 node but retains subsequent audit and revocation rights.
The scope of the delegation SHOULD be specified in the NodeCertificate (for example, limited to specific `contact_type` values).

ContactType enum:

```text
0x0001 Contract signing (both parties are signatories)
0x0002 Data exchange (information transfer)
0x0003 Payment settlement (transfer of value)
0x0004 AI collaboration (cross-universe AI interaction)
0x00FF Other
```

**Causal semantics of a CSR:**

After a CSR is established:

All events in Universe A at `t_A < TI_A` are not directly observable to Universe B (the universes remain independent).  
All events in Universe B at `t_B < TI_B` are not directly observable to Universe A.

After the contact surface:

If event `E_B'` occurs in Universe B (`TI_B' > TI_B`) and its SemanticAnchor references the CSR, then the following can be proven:

```text
E_A (TI_A) ≺ CSR ≺ E_B'
```

This is the only cross-universe causal proof needed; TI alignment is unnecessary.

### 4.5 Federation exit and revocation

Voluntary member exit:

Step 1: The initiating member submits an exit request (`ExitProposal`).  
Step 2: The other federation members sign their confirmation (at least `amendment_threshold` signatures).  
Step 3: After it takes effect, publish an FMR (`event_type = 0x02`).  
Step 4: Historical CSRs remain valid permanently and are unaffected by the exit.  
Step 5: After the TI at which exit takes effect, federation members no longer trust the exiting party's THKs.

Member expulsion (serious violations):

Step 1: Other federation members jointly initiate an expulsion proposal.  
Step 2: At least `amendment_threshold + 1` members must sign.  
Step 3: Expulsion takes effect immediately (the expelled member's consent is not required).  
Step 4: Broadcast an FMR (`event_type = 0x02`, including a hash of the reason for expulsion).  
Step 5: The expelled member's THKs become invalid immediately (as if the L1 node were revoked); see §4.3.

Federation dissolution:

All members sign a dissolution resolution.  
Historical records are retained permanently.  
All previously issued EEAs and CSRs remain valid (history cannot be revoked).

## 6. Security considerations

### 6.1 Single-domain security

**Time-source tampering:**

Defense: use multiple time sources (BeiDou + NTSC + local atomic clock) and take the median.  
Detection: alert if `ti_growth_rate` in the THK chain is abnormal (deviation greater than 10%).

**Root-key leakage:**

Defense: Level 4 GM/T 0028 HSM, two-person authorization, and Shamir (3,5) key shares.  
Response: immediately publish a KeyRevocationRecord (`0x0012`) and have L2 nodes reject KeyPackages with the old `key_version`.

**ChildTHK trust propagation:**

A ChildTHK signer (operational key) may be different from the root key.
A verifier MUST trace back to the RootTHK and validate the ChildTHK's `parent_root_thk_id`.
It MUST NOT accept temporal authority based only on the ChildTHK signature.
The OpCertificate provides assurance that the operational key is valid (see §2.4).

**ChildTHK replay protection:**

The L1 node records the largest `sub_sequence` under each parent RootTHK and rejects duplicate sequence numbers.
A verifier SHOULD cache recently received ChildTHK sequence numbers and reject a duplicate (`E009`).

### 6.2 Federation security

**Malicious member (malfeasance within the federation):**

A single member cannot forge another member's signature.
A CSR requires signatures from both parties; one party alone cannot construct a valid cross-domain contact surface.
The expulsion mechanism allows `amendment_threshold + 1` members to expel a malicious member.

**FederationCharter forgery:**

Every member signature in a FederationCharter can be independently verified.
Forging a charter would require forging every member's SM2 signature, which is computationally infeasible.

**Cross-domain temporal-order deception:**

An attacker claims that event `E_A` in Universe A precedes event `E_B` in Universe B, but no CSR actually connects `E_A` and `E_B`.

→ Defense: cross-universe ordering MUST be proven through a CSR.  
Without a CSR, no ordering can be claimed; it is not that “A precedes B by default.”

**Reference validation in cross-domain verification:**

When `check_cross_ref=true` in a `CheckCrossUniverseEEA` request, the verifier SHOULD check whether anchors from other universes referenced by `EEA.SemanticAnchor` are valid (by querying a verification node in the other universe).
If verification is impossible (the network is unavailable or the other party does not respond), return `W006` (`FEDERATION_PARTIAL`) and mark the corresponding `cross_ref_status` entry as `3` (unverifiable).

### 6.3 Epistemic boundaries of the federation

What federation mutual recognition guarantees:

“In Universe B, EEA_B existed at TI_B and has not been tampered with.”
This is a guarantee within Universe B.

What federation mutual recognition does not guarantee:

The absolute physical-time correspondence between TI values in Universe A and Universe B.
(The clocks of the two universes may have systematic offsets; this is accepted.)

Design intent:

The federation needs “mutual recognition of causal relationships,” not “absolute time alignment.”
This is a lower requirement than GPS time synchronization and is also the more correct design.

## 7. Test vectors

### 7.1 RootTHK test vector

```python
# Test vector with fixed inputs, used to verify implementation correctness.
# In production, use real physical time and a CSPRNG.

import hashlib

def sm3(data: bytes) -> bytes:
    """SM3 (SHA3-256 is substituted here for demonstration; use a national-cryptography implementation in production)."""
    return hashlib.sha3_256(data).digest()

# Fixed inputs
t_utc           = 1748736000000000000  # fixed nanosecond timestamp
t_epoch         = 1000000001           # starting TI value
ti_range_start  = 1000000001
ti_range_end    = 4600000001           # covers 3,600,000,000 TIs
nonce           = bytes.fromhex("0102030405060708090a0b0c0d0e0f10")
l1_node_id      = bytes.fromhex("aa" * 32)
prev_commitment = bytes.fromhex("00" * 32)  # first RootTHK

# Compute time_commitment
def compute_time_commitment(t_utc, t_epoch, l1_node_id, nonce):
    payload = (
        t_utc.to_bytes(8, 'big')    +
        t_epoch.to_bytes(8, 'big')  +
        l1_node_id                   +  # 32 B
        nonce                            # 16 B
    )
    assert len(payload) == 64
    return sm3(payload)

time_commitment = compute_time_commitment(t_utc, t_epoch, l1_node_id, nonce)

# signing_payload (RootTHK signing input)
def compute_root_thk_signing_payload(
    t_utc, t_epoch, ti_range_start, ti_range_end,
    prev_commitment, time_commitment
):
    domain_tag = b"Prime.RootTHK.v1"  # 16 B
    payload = (
        domain_tag                          +
        t_utc.to_bytes(8, 'big')           +
        t_epoch.to_bytes(8, 'big')         +
        ti_range_start.to_bytes(8, 'big')  +
        ti_range_end.to_bytes(8, 'big')    +
        prev_commitment                     +  # 32 B
        time_commitment                        # 32 B
    )
    assert len(payload) == 16+8+8+8+8+32+32  # = 112 B
    return sm3(payload)

signing_payload = compute_root_thk_signing_payload(
    t_utc, t_epoch, ti_range_start, ti_range_end,
    prev_commitment, time_commitment
)

print(f"time_commitment:   {time_commitment.hex()}")
print(f"signing_payload_h: {signing_payload.hex()}")
# Implementations MUST match this output when using the same SM3 implementation.
```
